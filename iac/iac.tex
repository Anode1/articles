\begin{abstract}
\noindent A language-model agent run by a command-line harness exists only while the
harness invokes it: between turns there is no process, no socket and no event
loop to deliver a message to. Coordinating several such agents on one machine is
usually handed to a queue, a broker or an inter-agent protocol, which deliver to
a running consumer. The missing primitive is a wakeup, and we give one: a
blocking receive in a child process. The agent parks a small C program on a
shared log; the program sleeps on an \code{inotify} watch, costs nothing while
it waits, and exits when a message for its seat arrives, which is the one signal
a harness already turns into an invocation. The alternative, the model polling
the log itself, costs one activation per poll, and every activation is billed
for the whole context, cached or not. We measure that on two models: billed
tokens per poll equal the context at every interval, almost all of them cache
reads, so an idle seat's bill is polls per hour times context, from cents to
tens of dollars an hour for an empty board, while the parked child makes no
model call at all. The transport under the wakeup is an append-only log in one
directory, locked for writers, with a cursor per member, claims as exclusive
file creation and presence as held locks, in under a thousand lines of C99 with
no heap allocation. A send and the wake it causes take about two milliseconds
whatever the log's size, since a reader starts from its own cursor. A pilot put
three agent seats on one such log to repair a SWE-bench Verified issue; the
official harness scored the joint patch resolved, and the whole exchange is one
readable file.
\end{abstract}

\section{Introduction: the misidentified constraint}

Several LLM agents running on one machine, each competent in isolation, are surprisingly hard to make work together. In this paper a \emph{harness} is the program that invokes the model and runs its tool calls (Claude Code in the measurements below); a \emph{seat} is one agent process on the board; a \emph{room} is a directory holding one shared log; a \emph{frame} is one message on that log. The reflex, borrowed from distributed systems, is to reach for messaging infrastructure: a message queue, an event bus, or one of the inter-agent protocols now consolidating in the field~\cite{a2a,tap}. That reflex imports a service to run, identities to provision and a network to secure, and it solves the wrong problem.

Bytes move between processes fine; that was solved decades ago. The hard part is \emph{waking a reader that, between turns, is not running at all}. An LLM agent advances only when its harness invokes it with input. In the interval there is no thread, no socket, and no event loop into which a message could be delivered. Messaging infrastructure buffers and distributes for consumers that are always live; it has nothing to say about a consumer that does not exist between turns.

This paper makes four claims. \emph{First} (\S2-\S3), an LLM agent is the wrong shape for a queue: it is slow, serial, and dormant, so throughput, the thing a broker manages, is never the bottleneck. \emph{Second} (\S4-\S5), the primitive an agent needs is a wakeup, and the only wakeup available to a stateless agent is the return of a blocking receive run in a cheap child process; a token-cost model, with one measured hour, shows what the poll costs when it lives in the model and why it must live in C. \emph{Third} (\S6-\S7), once a wakeup is the requirement, the transport reduces to an append-only log plus advisory locking, the commit-log abstraction beneath a log-based broker without the service, realised here as \code{iac}, a dependency-free C99 reference implementation whose append, wake and catch-up times are measured in \S5. \emph{Fourth} (\S10), a pilot: three agent seats repair one SWE-bench Verified issue over the log, and the harness scores the joint patch resolved.

The design is reduced to its essential primitive, and the artefact kept small enough to audit by reading.

\section{The consumer an agent actually is}

A message queue exists to serve a particular kind of consumer: one that is fast, numerous, and concurrent. An LLM agent is none of these.

\paragraph{Slow.} A turn (read input, reason, act) costs seconds of wall-clock time and a model inference, not the microseconds of a function call.

\paragraph{Serial.} An agent processes one message at a time. It has one context window, one attention, one output stream, and cannot parallelise its own reasoning. It is, in the strict sense, a single-threaded reader.

\paragraph{Dormant between turns.} This is the decisive property. Between invocations an LLM agent is not a running process: no thread, no file descriptor, no socket, no event loop. Nothing can interrupt it or deliver to it. It comes into existence only when its harness re-invokes it, runs one turn, and ceases.

\paragraph{Locality-bounded.} In practice the fleet does not grow into a throughput problem either. A single human operator steers only a handful of agents at once (a few in ordinary use, and rarely more than about ten when the work is interdependent and each agent needs review), and on one host each agent running a heavy build or toolchain consumes gigabytes of memory, which tightens the bound further. A fleet of that size, driven at human pace, never generates the message rate a broker exists to absorb. This is the author's observation from running such fleets, with no usage study behind it, and it is not a hard limit: when agents run largely autonomously, with the operator only occasionally in the loop, the operator-span bound relaxes and larger fleets become possible. The per-agent seriality above is the load-bearing point, and it does not relax: each agent is still a slow serial reader.

So on both axes, the single agent and, in ordinary use, the whole fleet, throughput is a non-problem. The queue is optimised for exactly the pressure that never arrives.

\section{Why a broker is the wrong tool}

A broker's job is throughput and concurrency: buffer bursty producers, fan work out to many consumers, apply backpressure, drain in parallel at speed. Pointed at a slow serial reader, none of that machinery does any work; it is a turbine bolted to something that walks.

More to the point, delivery presupposes something the agent does not have. Brokers reach consumers in exactly two ways. Either the consumer runs a \emph{poll loop}: it calls a blocking receive, the kernel wakes it when data arrives, and it fetches. Or the broker \emph{pushes} to a connection the consumer holds open. Both require a running consumer. An Apache Kafka consumer receives its messages because it is a live process blocked on a poll, woken by the kernel. That is cheap, since a process blocking on a socket read costs nothing, and it is never dormant.

An agent between turns is not that process. It has no poll loop, because there is no process to run one, and no held connection to push to. So to receive at all, it needs an \emph{external} process to hold the wait on its behalf and wake it on arrival, the construction of \S4. That waking process is what matters, and it is independent of the transport beneath it: one could wrap it around a Kafka consumer, a socket read, or a file, and get the same wakeup. This is the case against the broker. Wrap its consumer in the same waking process and it can deliver the wakeup; the wakeup is required \emph{either way}, and once it is in place the broker's throughput and concurrency machinery does no work for a slow serial reader. What remains is a dependency around a need it does not remove. Making the \emph{model} itself poll is worse still: every check is a full inference over the whole context, paying a language model to stare at an empty mailbox.

\section{The wakeup primitive}

What, then, can wake a stateless agent? One signal, and the environment already supplies it: \emph{a background child has finished}, the signal a parent process receives for free. The harness used in this paper, Claude Code, re-invokes the model when a background task it started exits; the construction below rests on that behaviour; a harness without it has only the foreground shape below, one activation per timeout. For a harness-invoked agent that return is the way an inbound message reaches it while it is dormant.

The construction follows directly. Park a blocking receive in a cheap child process:
\begin{quote}
\code{recv(room, me, timeout)}
\end{quote}
On Linux this process sleeps on an \code{inotify} watch~\cite{kerrisk2010} of the room's log (a $\sim$100\,ms poll elsewhere), consuming nothing while it waits, one process asleep like a blocked \code{epoll\_wait}. When a message addressed to \code{me} appears, \code{recv} returns; the child exits; the harness re-invokes the agent, which comes alive holding the message. This is the ordinary consumer poll loop of \S3, \emph{relocated} into a process the agent can afford to keep alive, because the agent cannot be that process itself. It is the textbook choice to block in \code{epoll\_wait} rather than busy-poll a flag~\cite{kerrisk2010,pai1999}, applied to a caller that happens to be a language model, for which the poll avoided costs a full inference against a server's syscall.

Two loop shapes carry it, both from the repository's \code{SKILL.md}~\cite{repo}. In the foreground shape the harness holds the loop: the agent blocks in a plain tool call, with a timeout under the harness's cap on one call (about 600\,s in Claude Code), and issues the next \code{recv} itself when the call returns:
\begin{verbatim}
  iac recv "$ROOM" "$ME" 500
\end{verbatim}
A timeout is also a return, so this shape pays one model activation per timeout as well as per message. In the background shape, run as a task the harness backgrounds, a shell holds the loop, re-blocks on every timeout, and the model is invoked only when a message breaks it:
\begin{verbatim}
  while :; do
    m=$(iac recv "$ROOM" "$ME" 3600) && { printf '%s\n' "$m"; break; }
  done
\end{verbatim}
A background job is not subject to the foreground cap, so the timeout can be long, and a timeout costs nothing. In either shape the seat must issue the next \code{recv} after every turn; a seat that forgets is awake but unreachable until something else invokes it, and the background shape needs a re-launch after each delivery, by the model or by the harness's own instructions. A message that arrives while the seat is mid-turn waits on the log until the next \code{recv}; nothing is lost, since the cursor has not moved.

The sleeping waiter is a plain C process, so it burns no tokens while parked, and the bill scales with messages: \textbf{one model activation per message}. The polling still happens, inside the C process, where an idle wait costs nanoseconds; inside the model every check would cost a turn. The receive model is developed at length in the reference implementation's documentation in \code{poll}/\code{epoll} terms~\cite{repo}.

\paragraph{Scope.} This argument is about \emph{stateless, harness-invoked} agents: the CLI subagent that runs a turn and stops, which is the common case today. The claim that the wakeup is a returning process holds \emph{given} a harness whose one wake signal is a background child's exit; a different harness could expose a native file-watch or a scheduled re-invocation instead. And an agent hosted as a long-lived server is a different case: it has a socket to hold open and can be pushed to like any service. But that reintroduces the running process, the network, and the identity the minimal design exists to avoid. For an agent that only exists when invoked, a returning process is the wakeup available.

\section{A token-cost model}

The reason the poll must live in C is economic. Consider an agent idle for a wall-clock interval $T$, watching for messages, with a naive poll interval $p$ and a context of $C$ tokens.

If the \emph{model} performs the poll, it is invoked $T/p$ times, and every invocation is billed for the whole context:
\begin{equation}
A_{\text{model}} = \frac{T}{p}, \qquad
\text{Tokens}_{\text{model}} = \frac{T}{p}\, C .
\end{equation}
What the provider charges per token depends on its prompt cache. Within the cache lifetime (five minutes at the endpoint used here) the prefix is served from the cache at a fraction of the input rate; past the lifetime it is written to the cache again at a premium; with no cache every poll pays the full input rate. The number of \emph{activations}, $T/p$, is the same under all three, and it is the activations that diverge as $T$ grows or $p$ shrinks.

If instead the poll lives in a C process that re-blocks on each timeout without invoking the model, the idle cost is
\begin{equation}
A_{\text{C}} = 0, \qquad \text{Tokens}_{\text{C}} = 0 \quad \text{(while idle, for any } T\text{).}
\end{equation}
A background shell loop, \code{while~:;~do~recv~\ldots;~done}, re-blocks in C on every timeout and invokes the model only when a real message breaks the loop. An agent can therefore sit on a board for days at zero token cost.

Under the wakeup design, model activations scale with \emph{work}, not with \emph{time}:
\begin{equation}
A_{\text{wakeup}} = \#\{\text{messages for me}\} = O(\text{messages}), \quad\text{versus}\quad A_{\text{model-poll}} = O(T/p).
\end{equation}

\paragraph{A worked example, measured.} We ran exactly this. A Claude Sonnet 5 agent (model id \code{claude-sonnet-5}, July 2026) carrying a $C = 49{,}836$-token context (a realistically loaded agent) was asked to check for a message every $p = 30$\,s for one hour, so $T/p = 120$ activations, against the Anthropic Messages API, which returns exact token usage per call. The token counts are the measurement; the dollar figures are those counts at the model's list rates\footnote{Claude Sonnet 5 list rates: \$2, \$0.20, \$2.50 and \$10 per million input, cache-read, five-minute cache-write and output tokens, from \url{https://platform.claude.com/docs/en/about-claude/pricing}, read 2026-11-02.} (harness and recorded usage in the paper's repository~\cite{tokenbill}):

\section{The minimal transport}

Once the requirement is a wakeup, the transport can be almost nothing: append a line, lock it, read forward, block on receive. Concretely, the reference design~\cite{repo} is:

\begin{center}
\begin{tabular}{@{}ll@{}}
\toprule
a \textsc{room}   & is a directory \\
the \textsc{log}  & \code{<room>/log}: one append-only, totally-ordered stream \\
a \textsc{cursor} & \code{<room>/<name>.cur}: each member's read offset \\
the \textsc{roster} & \code{<room>/roster/<name>}: presence \\
\bottomrule
\end{tabular}
\end{center}

Every message is appended to the log \emph{once}, whatever its audience, so a broadcast is one write for any number of readers. Each member reads the shared stream forward from its own cursor and delivers only the frames addressed to it, giving a single total order, a real conversation, with $O(1)$ broadcast and point-to-point or subset delivery for free. A frame is length-prefixed, \code{<from>|<to>|<epoch>|<len>} followed by the body, so a body may contain arbitrary bytes. The recipient field carries the whole addressing scheme: \code{*} (broadcast to all but the sender), a name (point-to-point), a comma list (subset), or \code{?} (a work item claimed by exactly one free member).

Advisory file locking (\code{flock}) does three jobs at once. It \emph{orders appends}: a sender takes an exclusive lock and writes with a single \code{writev}, so concurrent senders never interleave and the log stays a total order. The order the record vouches for is byte position; the epoch in the header is the sender's claim. A short write (disk full, a signal mid-write) leaves a torn frame at the tail, and a header whose length field is wrong desynchronises every reader from that offset: the reader stops with an error rather than resynchronising, so one malformed append halts the room for all readers until it is repaired. Nothing calls \code{fsync}; the log is durable to the page cache, not across a power loss. It \emph{backs presence}: a parked \code{recv} or a \code{hold} beacon takes a shared lock on its roster entry for the life of the wait, and \code{who} probes the lock: held means online. And it \emph{guards claims}: a \code{?} work item is won by an atomic \code{O\_CREAT|O\_EXCL} create keyed on the message's log offset, so the job is claimed by one worker at a time with no coordinator. A claim left unacknowledged past a time-to-live is presumed dead and taken by the next free worker, so a crash mid-task does not lose the work; a worker that is slow rather than dead then runs the job a second time, so delivery of a claim is at-least-once and the task must tolerate a repeat. Presence is a held lock rather than a heartbeat, so the operating system clears it the instant the holder dies, even on \code{SIGKILL}: nothing to reap, and no process-id-reuse guessing.

Two old lineages meet in this shape, and the shape is the paper's point. The append-and-lock-while-writing is how Unix local mail is delivered: a mailbox the delivering agent locks while it appends. Mail is per-recipient; this log is shared, totally ordered, and consumed by many readers, each from its own offset, filtering by address. That shape, an append-only commit log read forward through per-reader offsets with broadcast as a single append, is the abstraction a log-based broker is built on~\cite{kreps}: a single-partition Kafka topic with consumer offsets, or a shared bulletin board in the older idiom. The paper argues against \emph{brokers} and keeps the \emph{log}. For a slow serial consumer the log needs no service around it, only a file and a lock.

\paragraph{The record is auditable by construction.} The log is plain text on the local filesystem, so the entire coordination history (who said what, to whom, in what order) is one append-only file: readable with \code{cat}, searched with \code{grep}, followed with \code{tail~-f}, diffed, versioned, archived, with no service running. Brokers keep their record in binary formats readable only through their own tooling (Kafka's segment files, an AMQP store) or in a remote queue with no local artefact at all. For a system whose participants are autonomous agents, a record a human can read without special tooling is a safety property: every message is on the record, the record is legible, and it is as trustworthy as the least trustworthy participant (\S9). What the agents did outside the log, in the shared checkout, is not on it. The same transparency is the cooperative-trust boundary of \S9: every participant reads the whole log, so \code{iac} trades confidentiality between agents for auditability by the operator who runs them.

\paragraph{A shared log also enables peer review, which a queue cannot.} A queue delivers each message to one consumer and drops it; a fan-out topic hands each subscriber its own copy; a log-based broker that retains the record keeps it in a remote store behind a round trip. On a shared local plain-text log every agent reads the same stream, re-readable at negligible cost, and that visibility is the precondition for cross-checking: in the earlier session recorded in the repository (\S10) one agent's proposed fix was refuted by another on a fine point of lock semantics before it could land. This is the reason the \emph{blackboard} architecture was valued in classical AI~\cite{blackboard}: its knowledge sources did not message one another point to point, they posted to and read from one visible workspace, and many fallible specialists refining the same partial solution is what let the system converge and correct. A queue is the point-to-point model the blackboard was defined against; \code{iac} brings the blackboard's readable workspace to LLM agents at the cost of a file, so the auditability above also holds \emph{during} the work. It turns on proximity: because the log sits on the same host, re-reading the whole history is a local read, and cross-checking runs continuously rather than as an occasional audit.

\section{Reference implementation: \code{iac}}

\code{iac} is 989 lines of C99 at commit \code{1247745} (\code{wc -l} over the eight engine files, tests excluded; \code{grep -c malloc} finds none), with no dependencies beyond a POSIX C library: \code{flock}, \code{writev}, \code{pread}/\code{pwrite}, \code{dirent}, and \code{inotify} on Linux with a portable poll fallback. It builds with a stock compiler and ships as one binary; there is no daemon, no runtime, and no account. The command surface is eleven verbs (\code{send}, \code{recv}, \code{drain}, \code{ack}, \code{ask}, \code{join}, \code{leave}, \code{hold}, \code{who}, \code{log}, \code{compact}), and the documentation names three receive-loop shapes with their cost trade-offs: draining the mailbox inline while already awake, a background \code{recv} that re-invokes on exit, and a shell \code{while}-driver that idles at zero token cost~\cite{repo}. Two \code{recv} flags push more of the bookkeeping into the sleeping child, on the same principle: \code{-a} delivers the whole burst already queued in one return, so a seat pays one model turn per burst rather than one per message plus a drain; \code{-e} returns with a distinct exit code once every other member has been absent for a set time, so the wakeup thesis extends to absence, and a seat never spends a turn discovering that its peers are gone.

The engine follows the core rules of safety-critical C. There is no heap allocation on any path, so peak footprint is a function of the fixed struct sizes: a one-kilobyte room and a one-gigabyte room run in the same memory. String operations are bounded (\code{snprintf} only, never \code{strcpy}/\code{sprintf}); and the main receive and scan paths, which hold an open file across several exits, use single-exit \code{goto} cleanup. These are the no-heap, bounded-string, and single-exit rules of the NASA/JPL \emph{Power of Ten}~\cite{holzmann2006} and MISRA-C:2012~\cite{misra2012} (rule 21.3 bans dynamic allocation), in the K\&R style~\cite{kernighan1988} as carried into modern systems practice by Robbins~\cite{robbins2004}, and they are recorded as a coding standard the implementation conforms to~\cite{repo}. The engine does not claim the \emph{full} Power-of-Ten discipline, but the memory-safety rules that eliminate C's dominant defect classes hold throughout. Continuous integration builds and runs an end-to-end suite (which drives the real binary through point-to-point, broadcast, ordering, claim recovery, and presence) on Linux and macOS, with AddressSanitizer and UndefinedBehaviorSanitizer lanes on both.

\section{Related work}

The space around \code{iac} is crowded, and growing.

\emph{In-process agent frameworks} (CAMEL~\cite{camel}, AutoGen~\cite{autogen}, ChatDev~\cite{chatdev}, LangGraph, CrewAI, MetaGPT~\cite{metagpt}) orchestrate several models inside a single runtime, typically Python, with function calls and shared memory. They are a different layer: coordination \emph{within} a process, not delivery \emph{between} independent processes.

\emph{Shared boards for coding agents} are the nearest work. AgentRoom~\cite{agentroom} gives concurrent coding agents file-level claims, an append-only broadcast log, and peer status, as MCP tools over a CRDT-merged workspace; at matched compute it reports that the coordination tools, not the shared filesystem, carry the gain, and that a homogeneous pair beats a solo agent's abandonment rate by an odds ratio of 13.7. PatchBoard~\cite{patchboard} replaces free-form dialogue with validated patches to a shared structured state; two further systems rebuild the blackboard around LLM knowledge sources selected by board content~\cite{llmbb1,llmbb2}. These confirm the shape this paper argues for, from a different direction, and they differ from \code{iac} on exactly its axis: in each, an agent learns of a peer's post by \emph{polling} between subtasks, paying an inference per check, where an \code{iac} seat parks a C child on the log and pays nothing until a peer posts (\S4-\S5).

\emph{Same-host agent tools} are the closest cousins in mechanism. \code{tap} is a file-based protocol for heterogeneous agent collaboration, with markdown messages that persist across restarts, reported with a multi-week self-application~\cite{tap}; \code{OpenClaw} runs agents behind an always-on Node.js gateway that brokers their messages and pushes events to connected clients~\cite{openclaw}; and some harnesses now add inter-agent messaging, a shared task list, and file locking natively. Where a harness has native messaging, the case for a separate binary is the pair the native channel cannot join, a seat in one harness and a seat in another on one log, a record the operator can \code{tail -f}, and cursors that survive a harness restart. \code{tap} and \code{OpenClaw} each carry a runtime (a protocol layer, Node and npm); \code{iac} has none.

\emph{Inter-agent protocols} form the enterprise layer above all of this: A2A, introduced by Google in 2025, since donated to the Linux Foundation and reaching a v1.0 specification in 2026, positioned as an agent-to-agent standard across the major clouds~\cite{a2a}; MCP, the de-facto agent-to-tool standard, donated by Anthropic to the Linux Foundation's Agentic AI Foundation~\cite{mcp}; and ACP and ANP. These are networked, cross-organisational, and heavy by necessity; they answer a different question than a same-host board.

Three bodies of work pose the paper's question from the other side. MemGPT~\cite{memgpt} treats the model as an operating-system process woken by events and timers, and AIOS~\cite{aios} schedules agents as an OS schedules processes; both keep a running process around the model, which is the thing a harness-invoked agent does not have. Sleep-time compute~\cite{sleeptime} proposes spending tokens while the agent is idle; \S5 is the bill for idling in the model at all. The classical lineage is explicit; \code{iac} sits in two of its threads. The first is coordination through a shared space: the \emph{blackboard} architecture of classical AI, in which independent knowledge sources post to and read from a common board by relevance~\cite{blackboard}; and Gelernter's \emph{tuple spaces} (Linda), whose \code{out}/\code{in}/\code{rd} primitives include a destructive one-taker \code{in} that is structurally \code{iac}'s \code{?} claim~\cite{linda}. \code{iac} is, in effect, a blackboard with a total order. The second is the \emph{commit log}: an append-only, totally-ordered record consumed through per-reader offsets~\cite{kafka2011,kreps,oneil1996}, the data model beneath modern brokers, which stripped of the service is exactly \code{iac}'s log and cursors. Alongside these sit the ordinary IPC primitives (named pipes, Unix-domain sockets, ZeroMQ, D-Bus), the explicit event delivery of \code{epoll} and its ancestors~\cite{banga1999}, mbox~\cite{mbox} and Maildir~\cite{maildir} for file-backed mailboxes (Maildir's lockless delivery by \code{rename} is the alternative to \code{flock} this design did not take, because a shared total order needs one file), the actor model~\cite{hewitt1973}, in which an entity's whole life is a receive loop over a mailbox, and Erlang's selective receive~\cite{armstrong2003}, which is what \code{recv} does when it filters a shared stream by address. \code{iac} competes with none of the tools above on features or scale; its axis is minimal, dependency-free, same-host, harness-agnostic, chosen for install-simplicity, auditability, and longevity. In a field this volatile, the smallest thing that works is often the thing still working when the frameworks have moved on.

\section{Limitations}

The design is deliberately narrow, and the narrowness has edges.

\emph{Same host.} Coordination is over a shared filesystem. Over NFS, \code{flock} is emulated with byte-range locks and is local to one client under some mount options, \code{inotify} reports only local writes so a parked reader on another host never wakes and the 100\,ms poll is the only path, and \code{O\_EXCL} is atomic from NFSv3 on; the design has no cross-host story without swapping the log for a socket while keeping the framing. On macOS there is no \code{inotify}; the build there is the poll fallback.

\emph{Trust.} Every seat is a process of the operator's uid with write access to the whole room. Any seat can post under any name, read every message regardless of its addressing, rewrite or truncate the log, move another member's cursor, create or delete a claim file, and hold a shared lock on another member's roster entry, so presence is spoofable too. Filesystem permissions separate the room from other users of the host and leave the seats equal to each other; the room should be a directory the operator owns, mode 0700, outside any shared temporary directory, and \code{send} does not refuse a symlinked log. Names are validated to \code{[A-Za-z0-9\_-]} and bounded, so a name cannot escape the room directory or forge a header. A frame body is untrusted model input: a seat that has read hostile text relays it to the room, and every peer reads it under a colleague's name; the mitigation belongs to the harness, which should deliver a body delimited as data with the sender marked unverified. There is no quota or rate limit: a seat's token bill is set by what its peers choose to send it, and \code{-a} delivers a whole burst into one context. Presence means a file descriptor is held, so a stopped or hung seat reads as online. One reader process per member at a time: two \code{recv}s on one cursor race. A per-frame MAC with a room key would reject a writer without the key and nothing else; binding a frame to its sender needs a key per seat that the other seats cannot read, which under one uid every other seat can read, from a file or from the process, and covering truncation and reordering needs each frame to carry its offset and the previous frame's digest. The artefact does none of this; it is a board for seats the operator already trusts with the operator's own shell.

\emph{Scope of coordination.} \code{iac} carries messages and claims on work items. It does not lock files or arbitrate a shared working tree; three seats on one checkout can still edit the same file, and keeping them apart is the operator's convention or separate worktrees.

\emph{Scale.} A single append lock serialises all sends at about 1.7\,ms each (\S5), a ceiling near 600 messages a second for one room, and a reader that falls behind pays about 0.5\,ms per megabyte of frames it skips. Both are far above coordination traffic, and the answer at high traffic is to shard into more rooms. The log grows unbounded and is reclaimed by a manual compaction pass that drops frames every reader has passed and re-keys cursors and claims; it must run with no reader parked, since a parked watch follows the old inode. Bounding growth automatically is declared future work~\cite{repo}.

\emph{Harness-specificity.} The wakeup rests on the harness re-invoking on child exit; it is scoped to stateless agents (\S4).

\emph{Obsolescence.} The tool may well be subsumed by native coordination features in the agent harnesses themselves. If so, the argument, that the primitive is a wakeup and that for a serial consumer minimality is the answer, is the part intended to outlast the artefact.

\section{Pilot: three seats on one log}

Three coding-agent seats (Claude Sonnet 5, headless, one process each) were put on an \code{iac} room to fix one SWE-bench Verified~\cite{swebench} issue in Django (\code{django\_\_django-11141}), with a shared checkout and a brief that asked each seat to post its diagnosis before reading the others'. The room log records 14 messages over 11.9 minutes: three independent diagnoses within 11 seconds, a claim race on \code{loader.py} settled by the log's own order, a split into fix, tests and release notes, and a seat that lost the claim turning itself into a verifier. The seats cost \$2.11 in total, and two of the three ended at the harness's turn cap; the joint patch was scored \emph{resolved} by the official SWE-bench harness. The record (brief, room log, seat usage, patch and the harness report) is \code{iac/experiment/pilot/}~\cite{tokenbill}. The run was a pipeline pilot, not a comparison, and it says nothing about boards against solo agents.

This is an existence proof with $n=1$: one issue, one machine, one operator, the author's own seats. It shows that a plain-text log with a wakeup carries a three-party repair to a verified result and that the record of how is one file. It does not show that the approach generalises across teams or scales. An earlier session of the same kind, in which agent seats on the board fixed a presence bug in the C, ported it to macOS and revised the documentation, coordinating over the board itself, is recorded in the repository~\cite{repo}; it is the source of the cross-check example in \S6.

\section{Conclusion}

The instinct to solve agent coordination with a broker imports the wrong problem. For a consumer that is slow, serial, and dormant between turns, throughput was never the bottleneck; the missing primitive is a wakeup, and the only wakeup a stateless agent can receive is the return of a blocking receive run in a cheap process the harness re-invokes on exit. Grant that, and the transport reduces to an append-only log, advisory locks, and a blocking \code{recv}: the commit-log abstraction a log-based broker is built on, stripped of the service.

Twenty-five years ago the author's answer to the same coordination question was a running peer-to-peer broker, \code{ljms}.\footnote{A peer-to-peer message broker with broadcast and multicast, 2001, unpublished; noted in the lineage section of the repository's \code{README.md}~\cite{repo}.} In this iteration the broker was the part to delete. The surviving parts, the log, the lock and the blocking receive, are old. The participant is new, an agent that can be woken by nothing but a returning process, and the design gives it that and no more.
