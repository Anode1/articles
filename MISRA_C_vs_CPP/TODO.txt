# Objective

Continue developing the paper **“Textual Compression vs. Semantic Reconstruction: Measuring Programming-Language Complexity for AI Coding Agents.”**

The goal is not to prove that C is better than C++. The goal is to execute a controlled experiment that can falsify the hypothesis that explicitness and reduced semantic indirection lower AI-agent maintenance cost.

The central conceptual model is:

[
\text{Program Representation}
\rightarrow
\text{Retrieval}
\rightarrow
\text{Semantic Reconstruction}
\rightarrow
\text{Modification}
\rightarrow
\text{Verification}.
]

Do not turn this into an advocacy paper for C.

---

## 1. First: inspect the actual implementations

Before designing or running agent experiments:

1. Inspect the existing `ais` C implementation.
2. Inspect the C++ implementation used for the preliminary comparison.
3. Determine exactly which source files belong to the benchmark subsystem.
4. Establish the behavioral specification of the subsystem.
5. Identify all externally observable behaviors.
6. Determine whether the two implementations are actually behaviorally equivalent.
7. Record the exact compiler/toolchain versions.
8. Determine exactly how the existing LOC/token measurements were produced.
9. Reproduce the preliminary measurements independently.

Do not trust the existing 26% token figure until the counting procedure is documented and reproducible.

Record:

* comments included/excluded
* whitespace included/excluded
* headers included/excluded
* generated files included/excluded
* macros
* preprocessor output
* tokenizer/tool used
* tokenizer version
* exact files counted

# 2. Construct the benchmark implementations

Ideally the experiment should contain four conditions:

### A. Restricted C

The existing explicit `ais`-style C.

Characteristics:

* explicit state
* small functions
* explicit resource management
* bounded data structures
* limited preprocessing
* limited pointer use
* shallow relationships
* explicit error handling

### B. Conventional C

A competent C implementation of the same behavior without deliberately applying the restricted style.

This condition is important because otherwise “C vs. C++” is confounded with “author's preferred style vs. modern C++.”

### C. Idiomatic C++17

A professionally written modern C++ implementation.

Allow appropriate use of:

* `std::string`
* `std::vector`
* standard library
* RAII
* classes
* constructors/destructors
* appropriate standard abstractions

Do NOT intentionally make it convoluted.

### D. Abstract C++

A second professionally defensible C++ implementation using more abstraction where appropriate:

* interfaces
* inheritance
* generic components
* additional abstraction layers
* callbacks where justified
* additional type indirection

The goal is not to create a straw man.

---

# 3. Establish behavioral equivalence

Create a language-independent behavioral specification.

The specification should describe behavior, not implementation.

For example, prefer:

> “When an existing posting is inserted, the operation must…”

rather than:

> “Modify `post_insert()`…”

Create comprehensive tests covering:

* normal behavior
* empty inputs
* maximum-size inputs
* duplicate entries
* ordering
* boundary positions
* invalid input
* I/O failures
* resource failures
* cleanup
* error propagation

Run the same behavioral specification against every implementation.

---

# 4. Create maintenance tasks

Create at least 20 independent tasks initially.

Divide them into:

### Local tasks

Examples:

* add validation rule
* change encoding behavior
* change duplicate semantics
* add a count operation

### Cross-module tasks

Examples:

* change path semantics
* change ordering behavior
* change stream behavior
* modify error propagation

### Debugging tasks

Examples:

* introduce and repair duplicate-handling bug
* introduce and repair resource-management bug
* introduce and repair failure-path bug

Every task must require actual comprehension.

Avoid:

* simple search-and-replace
* tasks where the target function is explicitly named
* tasks solvable from one line
* tasks depending on undocumented external knowledge

The agent should be told WHAT behavior must change, not WHERE to change it.

---

# 5. Hidden tests

Every task needs hidden tests.

The agent must not see them.

Visible tests may establish the basic behavior.

Hidden tests should probe:

* boundary cases
* failure cases
* cases not represented in visible examples
* interactions between modules
* regressions

The objective is to prevent the agent from merely optimizing for visible examples.

---

Run the same task across each implementation.

At minimum:

# 7. Do not contaminate the experiment

The agent must not know:

* which implementation is expected to win
* the research hypothesis
* that C is the “explicit” condition
* which files are expected to be difficult
* hidden-test details
* the location of the implementation

Use the same neutral task instructions wherever possible.

The experiment should be blind with respect to the hypothesis.

---

# 8. Measure retrieval separately from reconstruction

Do NOT use “context tokens” as the only complexity measure.

Record at least:

### Retrieval

* files searched
* files opened
* lines read
* search operations
* retrieved tokens
* cumulative input tokens
* irrelevant/redundant context where measurable

### Reconstruction/exploration

* unique symbols inspected
* dependency edges traversed
* cross-file transitions
* semantic relationships explored
* call-chain depth
* number of alternative implementations considered
* time before first modification

### Modification

* files changed
* lines changed
* number of edit operations
* number of iterations

### Verification

* compilation failures
* visible-test failures
* hidden-test failures
* regressions
* corrective iterations

### Outcome

* success/failure
* final correctness
* unrelated modifications
* wall-clock time
* model execution time
* tool time

# 9. Develop a semantic graph

This is an important part of the research.

Construct a graph for each implementation.

Nodes can include:

* functions
* methods
* variables
* structs
* classes
* interfaces
* templates
* modules
* files

Edges can include:

* calls
* references
* inheritance
* implementation
* overriding
* template instantiation
* conversion
* ownership
* dispatch
* callbacks

Do not initially force everything into one SID scalar.

Measure several quantities:

### Semantic distance

How many relevant relationships must be traversed?

### Semantic breadth

How many relevant entities are potentially involved?

### Semantic ambiguity

How many plausible targets/interpretations must be resolved?

### Dependency dispersion

How widely across files/modules are the relevant entities distributed?

Then determine experimentally which of these correlates with agent maintenance cost.

---

# 10. Be careful about C++ abstractions

Do NOT assume:

> C++ abstraction = bad for AI.

Explicitly look for cases where C++ reduces complexity.

Examples:

* RAII may simplify resource lifetime.
* `std::vector` may eliminate complicated manual memory management.
* strong types may eliminate invalid states.
* encapsulation may prevent unrelated code from needing to inspect internals.

The paper should be able to discover both positive and negative effects.

A particularly interesting result would be:

> Some abstractions increase semantic distance but decrease semantic ambiguity.

That would be a valuable result.

---

# 11. Statistical analysis

Do not treat:

```text
20 tasks × 5 repetitions = 100
```

as 100 independent observations.

Repeated runs share the same task.

Use a statistical approach appropriate for repeated observations, ideally mixed-effects models.

For continuous outcomes such as context tokens:

* consider log transformation
* mixed-effects regression
* task as random effect
* model as random effect where applicable

For success/failure:

* mixed-effects logistic regression

Report:

* effect size
* confidence interval
* p-value where appropriate
* raw distributions
* per-task results

Do not rely solely on statistical significance.

---

# 12. Define a primary outcome BEFORE running the experiment

Choose one primary outcome.

A good candidate is:

> cumulative agent input/context tokens required to reach a correct solution

but also analyze:

* success probability
* tool calls
* exploration
* iterations
* failures

Be careful with conditioning on successful runs because unsuccessful runs can themselves be informative.

Pre-specify how failures will be handled.

---

# 13. Investigate the retrieval interaction

This may become the strongest part of the paper.

Ask:

> If AIS retrieves exactly the relevant information, does the difference between explicit and abstract representations disappear?

There are two interesting outcomes.

### Result A

AIS eliminates most of the difference.

Interpretation:

> The problem was primarily information retrieval.

### Result B

AIS reduces the absolute cost of both implementations but the relative difference remains.

Interpretation:

> Representation itself affects semantic reconstruction.

This distinction should be central to the analysis.

# 15. Improve the paper around the central framework

The paper should revolve around:

[
\boxed{
\text{Representation}
\rightarrow
\text{Retrieval}
\rightarrow
\text{Semantic Reconstruction}
\rightarrow
\text{Maintenance}
}
]

Do not let it drift back into:

> C is simpler than C++.

The scientifically interesting question is:

[
\text{textual compression}
\not\Rightarrow
\text{semantic compression}
]

and whether this relationship is observable in real AI coding agents.

# 18. Add a section explicitly discussing possible outcomes

At minimum:

### Outcome A

C is larger but cheaper for agents.

Supports semantic reconstruction hypothesis.

### Outcome B

C and C++ are similar.

Weakens the hypothesis.

### Outcome C

C++ is smaller and cheaper.

Rejects the hypothesis.

### Outcome D

Results depend on task type.

Potentially the most interesting outcome.

### Outcome E

Retrieval determines the result.

Suggests that representation effects are secondary to retrieval.

### Outcome F

Different abstractions have opposite effects.

This would support a more nuanced theory of AI-oriented abstraction.

# 19. Do not manufacture results

The paper currently has placeholders.

Keep them.

Do not write conclusions about the agent experiment until it has actually been run.

If an experiment fails, say so.

If results are inconclusive, report that.

If C++ wins, the paper should say C++ wins.

That is essential to the credibility of the project.

# 20. Final paper editing

After the experiment is complete:

1. Replace placeholders with results.
2. Remove speculative language that is no longer necessary.
3. Update hypotheses based only on preregistered analysis.
4. Add tables and figures.
5. Add confidence intervals and effect sizes.
6. Add raw/per-task distributions.
7. Explain unexpected results.
8. Update Threats to Validity.
9. Make the conclusion reflect the actual data.
10. Ensure that no sentence implies a result that the experiment did not establish.

The final paper should be presented as an empirical study, not as an argument for procedural programming.

# One additional experiment worth considering

If feasible, create a fourth/fifth representation of the SAME behavior where you deliberately vary only semantic indirection.

For example:

```text
Direct C
   ↓
one additional abstraction layer
   ↓
two abstraction layers
   ↓
interface + implementation
   ↓
interface + inheritance + generic layer
```

If agent cost increases monotonically with controlled increases in semantic indirection, that would be much stronger evidence than simply observing C versus C++.

That experiment could potentially turn the paper from a language comparison into a general theory of **semantic reconstruction cost**.
