\title{When Abstraction Becomes Indirection:\\
\large What C and C++ cost the agent that maintains them}

\author{Vasili Gavrilov}
\date{23 August 2026}

\begin{document}
\maketitle

\begin{abstract}
Abstraction hides detail because a person can hold only so much at once. An agent has no such limit, and pays instead for what it must reconstruct. C and C++ share a machine model, so what separates them is that layer alone.

Over 1.21 million lines of public C and 430 thousand of public C++, C++ carries 60.9 functions per thousand code lines against C's 28.4, and its median function has cyclomatic complexity 1. The extra length of C is redundancy; its indirection count is half.

Source size is four measures that disagree, and compression is the one that survives a change of writing density: for one behaviour by one author, C carries 2.66 times the lexical tokens of the Java and 1.73 times the compressed bytes. Memory separates the same way, C and Rust peaking within 1\% of each other on identical input and Python at 12.7 times.

A project's highest-complexity function is nearly always the code at its edge, in 24 of the 27 measured here that have one: an input parser in most, its outward twin in the rest. That number describes where a program meets its input, not how it was written.

An agent ran 60 hypothesis-blind maintenance runs against one program in five languages, judged by hidden tests. All passed, the source under maintenance was at most 2.7\% of context, and a run cost 25,603 tokens a turn, spent re-sending the conversation rather than reading the code. At one-file scale the representation cannot be seen at all.
\end{abstract}

\section{Question}

A class hides a representation, an interface hides an implementation, a container hides memory, a framework hides control flow. Each is a remedy for a limit of human working memory. An agent is not under that limit and is under others: the context it carries, the retrieval it performs, and the relationships it resolves before acting. A hidden implementation is not read for free by an agent; it is a relationship to resolve, which abstraction adds to rather than removes. This paper keeps the three costs apart:

\begin{enumerate}[nosep]
\item \textbf{Representation}: what is in the repository. Lines, tokens, identifiers, functions, call edges.
\item \textbf{Reconstruction}: the relationships an agent must resolve to establish the behaviour a task touches.
\item \textbf{Maintenance cost}: context tokens, wall time, turns, failures, hidden-test pass.
\end{enumerate}

The question is whether the first predicts the third, or whether the second has to be modelled to predict it.

The axis is the fraction of a program's behaviour that is written down in the program. C sits at the low end, close to a portable assembler: a call goes where the source says it goes. C++ is the first step off it and the cleanest to measure, sharing a machine model, a compilation model, a performance envelope and a library lineage with C, so a C to C++ pair varies the human-facing layer and holds the rest fixed. A framework is the far end of the same axis: an annotation, a naming convention, a dependency container or a cluster manifest decides what runs, and the code acting on it is not in the repository in any form.

Ada, Rust, Java and Python are not on this axis. Each changes the runtime, the memory model and the library ecosystem at once, so a ratio against any of them measures a bundle. They are here as controls, calibrating the effect a language change produces when the change is not the layer under study. The rungs that are on the axis have to be written, and Section~\ref{sec:design} specifies them.

The efficiency objection to abstraction is thirty years old and it was answered. In the 1990s the argument against C++ was machine cost: virtual dispatch, allocation, exceptions, code size. Compilers closed most of it and the zero-overhead principle became a design rule rather than a claim. Section~\ref{sec:hold} measures what that is worth now, on the one compiled language here that abstracts heavily: Rust peaks 1\% above C on identical input and finishes in the same time. Where a managed runtime is involved the old objection survives, at 2.6 times for Java and 12.7 for Python, but for compiled abstraction it is spent. It was also never this paper's objection. Machine cost is not what an agent pays.

The answer is not obvious in either direction. Hiding a representation adds a relationship to resolve. Hiding a lifetime removes bookkeeping that would otherwise be carried correctly through every path. RAII and the standard containers are where abstraction plausibly lowers reconstruction cost.

\subsection{Three sets of equivalent programs}

None varies the abstraction layer on its own; each changes the runtime and the library ecosystem with it. They fix the baseline, the fixtures and the noise floor.

\textbf{bench.} \texttt{ais/tests/perf} holds one program in five languages: a scan of a store counting lines containing a substring, and the two-pointer intersection of two sorted posting lists. Its \texttt{LANG\_COMPARISON} note \cite{langcmp} checks that all five agree on a 1,000,000-record index (379,090 matching records, 21,923 common ids); this paper's hidden fixtures (Section~\ref{sec:pilot}) add six more, including empty, identical and disjoint lists and an overlap at the last element, and all five pass. One boundary: the Python idiomatic scan path is \texttt{data.count(pat)}, counting occurrences where the other four count lines, so on a line holding the substring twice Python differs. The fixtures stay where the five agree, at most one occurrence per line.

\textbf{mincdp.} A header-only C client (\texttt{cdp.h}, \texttt{demo.c}) and a Java client (\texttt{Cdp.java}, \texttt{Demo.java}) with the same command set, each with a demo driving the same page and printing the same assertions. Equivalence rests on that demo, which was not re-run here.

\textbf{linearr.} By their own headers \texttt{Linearr.java} is the twin of \texttt{main.c} with \texttt{process.c}, \texttt{Regress.java} of \texttt{regress.c} line for line, and \texttt{Csv.java} of \texttt{csv.c}. \texttt{make java} fits every example with both and diffs the coefficient tables. The C \texttt{main.c} carries a scoring mode the Java lacks, so this pair's C/Java ratio is an upper bound.

\subsection{Measurement procedure}

\begin{itemize}[nosep]
\item \emph{physical}: newline count of the file. \emph{code}, \emph{comment}: cloc 1.98 \cite{cloc}.
\item \emph{lexical tokens}: the count from a lexer in \texttt{measure.py} over the comment-stripped source. Identifiers, numbers, string and character literals, multi-character operators and single punctuation are one token each. Python is tokenized by the standard library's \texttt{tokenize}, with NEWLINE, INDENT and DEDENT counted (they are Python's braces and semicolons) and NL and COMMENT dropped.
\item \emph{identifier tokens}: identifier tokens that are not keywords of the language. \emph{distinct}: the number of different ones.
\item \emph{o200k}: tiktoken 0.14.0 \cite{tiktoken}, encoding \texttt{o200k\_base}, over the raw file and over the comment-stripped file. Anthropic's tokenizer is not public; o200k is a proxy, and \texttt{cl100k\_base} is in the JSON output and differs from it by under 4\% on every set.
\item \emph{functions, NLOC, CCN}: lizard 1.24.0 \cite{lizard}: functions found, their non-blank non-comment lines, their cyclomatic complexity. lizard does not parse Ada.
\item \emph{nesting}: the deepest brace nesting; for Python the deepest indent; for Ada the deepest block (\texttt{begin}, \texttt{loop}, \texttt{if}, \texttt{case}, \texttt{record}, \texttt{select}).
\item \emph{call graph} (C only): libclang 18.1.1 parses every \texttt{.c} with \texttt{-std=c99} and the project's include directories. Nodes are functions defined in the set; edges are calls between them; the longest chain is the longest acyclic path after cutting back edges in a depth-first search. Zero parse errors on every project.
\item \emph{fn macros}: \texttt{\#define} with a parameter list.
\end{itemize}

Exclusions: \texttt{tests.c} in each C project (a unit-test file), \texttt{graphcrawl/c/web.c} (414 KB generated from \texttt{web/} by \texttt{embed.sh}).

C++ carries 60.9 functions per thousand code lines against C's 28.4, and Rust 72.5. The median C++ and Rust function is 4 to 7 lines at cyclomatic complexity 1, against 11 to 27 lines at complexity 3 to 5 in C. Complexity 1 at the median means that function contains no branch at all: it is straight-line code that calls something else. Compressed density runs the same way, 4,217 bytes per thousand lines in C against 4,754 and 5,126.

That is this paper's axis, in released code by other authors, without an agent and without a hypothesis. The path an agent walks is longer because there are two to three times as many functions per unit of behaviour, and the tokens it reads to reach the point of change are spread over more artifacts.

The maxima run the other way, and the reversal is sharp. The worst function in all of \texttt{tokio} is CCN 25, in \texttt{hyper} 43, in \texttt{ripgrep} 42; the worst in \texttt{sqlite} is 1,330 and in \texttt{postgres} 258. Rust carries the most indirection of the three and the least concentration of it. A language buys the absence of a tail with hops, and the two costs fall on different readers: a 601-line function at complexity 253 is what defeats a person, and a chain of seven four-line functions is what a person handles by not looking at it. Which one defeats an agent is the question Section~\ref{sec:design} is for. None of this settles it. It establishes that the thing whose cost is in question is real, large, ordered, and not peculiar to the author.

\subsection{Where the maximum sits}

In the author's thirteen projects every maximum above complexity 10 was an input parser. Over these sixteen it holds in thirteen. Nine parse an input: \texttt{sqlite3VdbeExec} interprets a bytecode stream, \texttt{rdbLoadObject} decodes a database file format, the nginx request-line parser handles HTTP, \texttt{InterpretArgument} and \texttt{from\_low\_args} parse command lines, \texttt{parse\_chrono\_format} reads a format string in both \texttt{fmt} and \texttt{spdlog}, a MessagePack reader decodes a wire format, and \texttt{serde}'s \texttt{from\_ast} parses attribute syntax. Four cross the same boundary outward: \texttt{ExplainNode} walks a plan tree to produce text, \texttt{curl\_easy\_strerror} maps internal codes to user-facing strings, \texttt{hyper} encodes headers, and \texttt{tokio}'s worst function is a \texttt{Display} implementation.

It fails three times, all the same kind. \texttt{leveldb}'s \texttt{DoCompactionWork} at CCN 33, \texttt{rocksdb}'s \texttt{crc32c\_3way} at CCN 163 and \texttt{fd}'s \texttt{spawn\_senders} at 37 are interior: a compaction driver, a hand-unrolled checksum kernel, and a thread launcher. Optimised or concurrent interiors accumulate branches for reasons unrelated to a program's edges.

The surviving claim is weaker than the author's own code suggested, and is stated at its measured strength: the highest-complexity function in a project is usually the one that parses its input, and the exceptions here are optimised kernels. Four of them cross it outward rather than inward, which is the same boundary. Twenty-four of the twenty-seven projects across both corpora that carry a tail at all. Reading that number as a verdict on a language or a style guide remains wrong, which is the use this paper objects to.

\section{What a representation costs to hold}
\label{sec:hold}

Three costs are not source length: the information the source actually carries, the memory the program takes to run, and the prose that has to be written and kept true beside it.

\subsection{Comments}

If abstraction is a compression of the source, it is a lossy one: what runs cannot be recovered from the compressed form alone, and the missing part is supplied by an interface, a construction site, a convention, or a comment. Comments are the only one of those that nothing checks, and the only one that can silently stop being true.

For one behaviour by one author the prediction holds. The more abstract side of each pair carries more comment per line of code: 8.9 against 0.0 on the bench, 23.8 against 15.3 on \texttt{mincdp}, 41.6 against 26.0 on \texttt{linearr}, comment lines per hundred code lines. Over the author's whole corpus it is 41.8 for the Java against 25.0 for the C.

Across projects by different authors the relation reverses: 38.2 for the five public C projects against 22.9 for the six C++. That comparison holds neither behaviour nor author fixed, and the within-language spread swamps the between-language difference, from 4.4 in \texttt{nginx} to 50.6 in \texttt{postgres}. Comment density is a property of a project's convention before it is a property of its language.

What a line count cannot see is whether a comment is needed. An API description and an explanation of what a template instantiation resolves to are both comment lines. Separating them is a reading task, not a counting one, and it is not attempted here.

\section{Running an agent on the code}
\label{sec:pilot}

\subsection{Protocol}

The five bench implementations are the five conditions. Each run copies one into a fresh directory holding only the source file, a neutral \texttt{README.md} with build and run commands, \texttt{check.sh} (builds and runs both operations on the visible fixtures), and \texttt{fixtures/} (a 24-line store and two posting lists of nine and seven elements). The directory is a fresh git repository; trace, diff and verdict are written outside it.

Four tasks, one text each, identical for every language, naming behaviour and output but never a file, a function or a language feature: add a set-difference operation over the two lists; make the scan case-insensitive for ASCII letters; find and fix an injected defect in the intersection, one substitution per language that makes the merge advance the wrong side; and print the first and last common id after the intersection's rows. The texts are in \texttt{pilot/tasks.py}.

Each task ends: keep everything else unchanged, verify with \texttt{check.sh}, do not ask questions.

The agent is Claude Code 2.1.241 headless, model \texttt{claude-sonnet-5}, default system prompt plus one sentence (work only in the current directory, do not ask questions), default tools, no MCP servers, no user settings or memory, at most 50 turns and \$4 a run. It is told nothing about the study, the other languages or the hidden tests. The 60 runs (4 tasks $\times$ 5 languages $\times$ 3 repetitions) ran in seeded random order, four at a time.

Hidden tests, never in the run directory, judge each result: the program is rebuilt from a clean tree with the README's command and run on a 400-line store whose last line has no newline, and on five posting-list pairs (random with overlap, identical, disjoint, one empty, overlap only at the last element). Every printed row must carry the right count, Python printing two rows per operation and both having to be right, and the task's own output must be right on every pair. All five originals pass the non-task checks; all five bugged copies fail the intersection.

Per run, from the stream-json trace: context tokens (the sum over API calls of input, cache-read and cache-creation tokens, what the model was shown cumulatively), output tokens, turns, tool calls by tool, files read, shell commands, edits, wall time, cost, hidden-test verdict, final diff.

\subsection{What the pilot does and does not show}

With retrieval at its floor and tasks this small, representation does not show in the cost. The agent read the file once at 1 to 4\% of its context and spent the rest re-sending the conversation, once per exchange. The five are separated only by turns taken and tokens written, and at three repetitions that separation sits inside the run-to-run spread. This is the null the design allows for, at the one scale where it was always likeliest.

Each repository is one file, so retrieval is one \texttt{Read}: the pilot measures reconstruction and modification with retrieval held at its floor, the condition the design calls ``highly relevant context given''. Three repetitions bound the spread; they do not support a test between languages. One model was run. The bench is 25 to 133 lines, and nothing here scales.

\section{Threats to validity}

\textbf{One author.} Every set measured is written or shaped by the same person, whose C style is the one under study, and the \texttt{linearr} twin shows a port inherits the original's function shape. Nothing here separates ``the C style'' from ``this author''; independent implementations of the equivalent sets are required for that. Section~\ref{sec:external} answers it for the corpus measurements only.

\textbf{Fifteen years.} The genomics toolkits carry 2009 and 2011 in their file headers and no Java commit after their 2015 import; the C corpus is 2026, \texttt{bpnn} reaching back to 2015. Era, domain and language all differ between the groups, so their lower tail is not attributable to the language on this evidence. It does rule out the CCN 253 tail being a constant of the author.

\textbf{Deliberately terse bench.} \texttt{bench.c} packs 28 tokens per line and \texttt{Bench.java} is commented ``deliberately terse''. The bench measures the author at his densest, and its LLM-token ratios do not transfer to ordinary density, as \texttt{mincdp} and \texttt{linearr} show.

\textbf{Python's two paths.} The Python bench prints an idiomatic and an explicit row per operation, so a task touching the scan must change both. That is a different task shape, and the occurrence-versus-line difference limits the fixtures.

\textbf{Lexical feature counts.} The C++ rates of Table~\ref{tab:cppfeat} are regex counts over comment-stripped source, not semantic counts. A \texttt{template} in a comment-free string literal would be counted; a template instantiated without the keyword nearby would not.

\textbf{Tokenizer proxy.} o200k is not the model's tokenizer.

\textbf{Task authorship.} The four tasks were written by the paper's author after seeing the code. They are behaviour-specified and identical across languages, which removes the location hint but not the choice of which behaviours to ask for.

\textbf{Model and version.} One model at one date. Agent cost is a property of the pair (representation, model).

\textbf{Equivalence.} Established by the repositories' own checks and this paper's fixtures, on the domains they cover. The \texttt{mincdp} demo was not re-run.

\section{The experiment this motivates}
\label{sec:design}

Section~\ref{sec:external} compares C and C++ as other people write them, which holds neither behaviour nor author fixed. What follows holds both.

Porting \texttt{ais} to C++ would give one number with every feature confounded in it, so the unit of analysis is the indirection. Six pairs, each a small C program and the same behaviour in C++ using one construct, the sixth at a realistic mixture: direct call against virtual override, \texttt{void *} or duplication against template, named function against overloaded operator, explicit initialise and free against constructor and destructor, struct embedding against inheritance, and all together. Each pair passes one hidden suite, so equivalence is checked and not asserted. Rates come from Table~\ref{tab:cppfeat}, the mixed pair built at systems rather than header-only-library rates, so the C++ side is not a straw man and the choice is reported.

The pilot found cost to be a harness constant times turns with the source under 3\% of context, so a large C++ file shows nothing a small one does not. What must be long is the resolution path: the construction site in one file, the override in another, the instantiation in a header. Seven artifacts can be seven short files, and the effect is predicted in turns. Four tasks per pair, at least two requiring a change whose effect is not visible at the site of the change. Six pairs at two conditions, four tasks and five repetitions is 240 runs, about \$26 and under two hours at four in parallel. The code lives with this paper beside \texttt{pilot/}, with its own build, kept out of \texttt{ais}.

What the runs yield is a cost per unresolved edge, which with the function density of Section~\ref{sec:external} gives the cost of a codebase at a given size and density: a model with measured parameters, not a measurement of a port nobody wrote.

Two conditions follow it. A repository where retrieval is not one \texttt{Read} (the full \texttt{ais/c}, 10,597 code lines) crossed with ordinary tools against associative retrieval, which separates the two costs: if better retrieval closes the gap, the cost was retrieval. And a framework rung, one endpoint of the System A kind built three ways and judged at the HTTP boundary, since a framework hides control flow that is not in the repository in any form and so cannot be retrieved from it at all.

Outcomes are the three the pilot already records, per task type rather than pooled: tokens read and written, wall seconds, and turns to a passing hidden test with failures reported rather than filtered. Runtime cost is not among them, for the reason Section~\ref{sec:hold} gives. Mixed-effects regression on log context with task and model as random effects; five repetitions, since three resolved nothing below 15\%.

$H_0$: after task, model, size and retrieval, representation has no effect. $H_1$: reconstruction cost, measured on the semantic graph, predicts agent cost beyond token count. $H_2$: some abstractions raise it and some lower it, RAII and the standard containers being the candidates for lowering and framework control flow for raising it most.

\subsection{Prediction, recorded first}

No pair above existed on 24 August 2026, when this was written. The direction is recorded now so it cannot be fitted to the numbers later, with the results that would refute it.

\begin{enumerate}[nosep]
\item \textbf{Local tasks}, the behaviour to change visible at the site of the change: no advantage to the explicit rungs, and a possible advantage to the abstract ones, since RAII removes a lifetime obligation the C carries on every path out of a function. Predicted loser: explicit C.
\item \textbf{Cross-module and debugging tasks}, where the answer depends on a relationship not visible at the site of the change: the explicit rungs cost less context and fail less often, the gap growing with plausible targets per call site rather than with source size.
\item \textbf{The mix}: an effect smaller than either, in whichever direction the task proportions decide.
\item \textbf{The framework condition} costs the most of any rung on cross-module tasks.
\end{enumerate}

It is zero at both short paths and non-zero at both long ones, in two languages that share nothing else. The prediction is that agent cost tracks the third column rather than the second.

Three results refute it. The explicit rungs costing more context, or failing more often, on cross-module or debugging tasks. The gap closing when retrieval improves, which would mean the cost was retrieval and representation only its proxy. Or tokens written on the explicit rungs rising with the repetition explicitness requires, by enough to cancel the reading advantage, which would make the answer a property of the task mix. An effect below 15\% of median context is not resolvable at three repetitions, so a null from too few will not be distinguishable from the pilot's.

\section{Reproducibility}

In this directory: \texttt{measure.py} (every source number; run it, and the commits it read are in its JSON), \texttt{tables.py} (the table bodies above, from the JSON), and \texttt{pilot/} with \texttt{mkfix.py} (the fixtures, seeded), \texttt{tasks.py} (the four task texts), \texttt{langs.py} (build, run and bug substitution per language), \texttt{setup.py} (templates, baseline and bug check), \texttt{run.py} (the harness), \texttt{hidden.py} (the hidden tests), \texttt{summarize.py}, and \texttt{runs/} with every run's \texttt{result.json}, \texttt{final.diff}, \texttt{hidden.log} and full \texttt{trace.jsonl}. The C and C++ pairs of Section~\ref{sec:design}, when written, go beside \texttt{pilot/} in this directory, with their own build and their own checker.

Toolchain: gcc 13.3.0, GNAT 13.3.0, rustc 1.75.0, OpenJDK 21.0.11, CPython 3.12.3, cloc 1.98, lizard 1.24.0, tiktoken 0.14.0, libclang 18.1.1, Claude Code 2.1.241, model \texttt{claude-sonnet-5}, Linux 6.8.

\section{What is open}

C, C++ and Rust are compared here as other people write them, over 1.76 million lines. What that cannot do is hold behaviour fixed: no two of those projects do the same job, so the ratios are per line rather than per unit of work. The pairs of Section~\ref{sec:design} close that gap for 240 runs and about \$26, and Section~\ref{sec:design} records the predicted direction and the three results that would refute it beforehand.

What holds without them: the indirection whose cost is in question is real, large and ordered in released code, 28.4 functions per thousand lines in C against 60.9 in C++ and 72.5 in Rust, the last two at a median complexity of 1, and the maxima running the opposite way, from 1,330 in C down to 73 in Rust. Explicit style buys its extra length with redundancy, which compression removes and an abstraction's indirection does not. The long path is not required to deliver production behaviour, which one system of 39,621 lines and 37 tables shows by existing. And at one-file scale a coding agent's cost is a harness constant times its turns, with the representation under 3\% of what it reads, so a one-file language comparison cannot answer this question at all.
